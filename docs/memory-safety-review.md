# Memory safety of the ZIM reader, writer and search tools

Reviewed on Linux x86-64, 18 November 2026. The starting revisions were MIT zimru `061afbc2920c78fc4ecb7211cb9ef4f3655dba35` and the separate GPL search companion `2162bfa8a2334d7fcda567c2491e614a4365baef`. This branch implements the storage migration and XZ encoder migration. **The shipped reader still invokes native code on archive-controlled Zstd and XZ bytes. A fully memory-safe stack remains a goal.** The original MIT license applies to this tree. The GPL index reader and writer stay in their own project. [Original zimru source](https://github.com/jasontitus/zimru/tree/061afbc2920c78fc4ecb7211cb9ef4f3655dba35)

## Which operations still cross an unsafe boundary?

| Operation | Implementation on this branch | Remaining trust |
|---|---|---|
| Open, look up or extract an uncompressed byte range | Checked, positioned reads on the original open file. A sharded cache holds up to 1 MiB of metadata page contents. A caller can read part of a multi-GiB blob into its own buffer. | OS reads and Rust dependencies. Cached data assumes stable file contents for consistency. Opting in to `legacy-mmap` accepts the caller's mapping and its lifetime contract. |
| Read a Zstd cluster | Native Zstandard through `zstd-sys`. Guarded reads bound compressed input, decoded output and the native history window. | Native C runs inside the reading process. |
| Write a Zstd cluster | Native Zstandard, including large-item streaming and worker support. | Native C runs inside the building process. |
| Read an XZ cluster | Native liblzma through `xz2` and `lzma-sys`. Guarded reads can also limit decoder memory. | Native C handles the compressed data and validates the container. |
| Write an XZ cluster | Upstream `lzma-rust2 0.25.0` with its optimization feature disabled. The writer streams into the XZ encoder, emits CRC64 and retains presets 0–9 and default 3. | The codec forbids its own unsafe code in this configuration. Its resolved SHA-256 support brings in unsafe Rust even though this writer selects CRC64. Reader-only builds omit the new encoder dependency. |
| Checksum and verify a new ZIM | Pure Rust `md5 0.8.1` over bounded reads from the same file, followed by structural verification on that handle. | MD5 serves the format's corruption check. It provides no publisher authentication. |
| Search the embedded Glass database | The companion uses the same open file for archive metadata and index blocks. Its CLI and Glass implementation forbid first-party unsafe code. The optional compressed-language fallback calls zimru's guarded decoder. | Rust dependencies implement text, compression and collections with internal unsafe code. ZIM codecs still link into the companion. Native Xapian is an external test reference. |
| Use the C/C++ API | Optional `cffi`. Archive and item range reads accept short reads and EOF, use a bounded initialized scratch buffer, and keep pinned blob views alive independently of parent handles. | Foreign callers control pointer validity, length, pin release and synchronization. A bad pointer or racing free cannot be validated by the exported Rust function. |
| Extract or run command-line tools | Unix extraction keeps directory FDs, no-follow traversal and atomic per-file publication via rustix. Unix read-ahead also uses rustix. | rustix, libc and the kernel implement these APIs. Two Unix CLI startup calls still use unsafe Rust to restore SIGPIPE. |

The library forbids first-party unsafe Rust in every build without the C API. With the C API enabled, the crate denies unsafe Rust and permits it in the FFI module. This lint does not propagate into dependencies. The Rust standard library, allocator and OS are additional trust boundaries in every build. ## Review findings and disposition

| Priority and area | Evidence, change and remaining work |
|---|---|
| High · mapped archive and writer output | The original reader mapped a file behind safe `Archive::open`. Another process can change or truncate a file without the mapping owner participating. The original writer also mapped its checksum input. Both operations now use the original descriptor. Renaming the path cannot switch the source of subsequent reads. In-place mutation can still give inconsistent results or a short read. The regular path never constructs a file mapping. `from_mmap` is a source-compatibility change for existing callers, who must explicitly enable `legacy-mmap`. |
| High · decoder limits and aggregate memory | `Archive::from_file_with_limits` bounds entry count, cluster count and metadata-record size before table allocation. Its optional cluster limits apply to all materializing cluster reads. Per-call limits can tighten them, including after cache population. Direct raw ranges remain usable without materializing the cluster. Title/offset tables have serialized fallible initialization, and named listings cannot exceed the entry count. The defaults retain broad format compatibility, including 4 GiB standard and 16 GiB extended logical decode ceilings. The default per-record metadata ceiling of 16 MiB is new and configurable. A decoded buffer can coexist with its final shared copy, concurrent calls can decode in parallel, caller-held blobs retain clusters, and the cache keeps one oversized entry. A strict process memory budget requires aggregate admission before decoding, a byte-accounted cache and a maximum on retained work. |
| High · writer ingestion and HTML inflation | `zimwriterfs` reads every HTML item in full and can retain up to 256 ready items before passing them to the byte-budgeted encoder. `--inflateHtml` uses `MultiGzDecoder::read_to_end` with no independent output cap. Large HTML, decompression and concurrent batching can exhaust memory before the encoder's own budget applies. Stream or spool large HTML, bound the inflated size and reserve aggregate input bytes before dispatch. The Glass builder has its own separate document and index budgets. [Writer input](../src/bin/zimwriterfs.rs) |
| High for foreign callers · C ABI | The generated header now specifies handle liveness, serialization for creators, disjoint writable buffers, error-slot ownership and single-release pins. New item/archive reads use initialized staging storage capped at 64 KiB even when the foreign caller supplies uninitialized output bytes. Callers of the legacy direct-access descriptor should use the same archive handle for reads. The Rust-only graph excludes this boundary. The unsafe surface belongs in a separately selectable adapter for deployments promising safe Rust to their callers. [Header](../include/zimru.h) · [Read adapter](../src/cffi/read.rs) |
| Medium · output, failure and filesystem semantics | Writer verification and splitting now use the same input/output handles as the operations they check. The writer still opens its destination with truncation before successful finalization. After a pipeline error the file handle may no longer be available to later writer operations. Use a terminal error state and an explicit close/publish step when adding transactional output. The illustration path is documented as relative but ordinary path joining/reading can select a source outside the HTML tree. Decide and enforce the source-root contract before packing untrusted input directories. Extraction constrains traversal, but distinct paths that sanitize to the same destination can replace one another. [Writer lifecycle](../src/writer.rs) · [Extraction](../src/bin/zimdump.rs) · [Directory packing](../src/bin/zimwriterfs.rs) |
| Medium · external builder | Previously the helper's stderr reader retained the entire stream. It now drains concurrently and keeps the last 64 KiB per process. Drop kills and reaps owned children on early exit. Ordinary feed, wait and stderr-thread join can still block on a stalled helper or inherited pipe. Add cancellation/deadlines covering all three and surface incomplete-index outcomes to deployments that require search. [Helper](../src/bin/_index_helper.rs) |
| Medium · dependency and assurance scope | Both original lockfiles matched RustSec unsoundness advisories RUSTSEC-2026-0002 and RUSTSEC-2026-0253 for `lru 0.12.5`. This branch uses 0.19.0. Both reviewed lockfiles returned zero RustSec vulnerabilities and zero warnings against database `233155b`. This is time-specific advisory matching. Native code can be statically included even when a dynamic-library listing has no matching entry. |

## Why the native readers remain

**Zstandard.** The isolated `zstd-rs 0.1.0` candidate forbids unsafe code and has zero production dependencies. On 65 native clusters its decoded output matched all 128,005,261 reference bytes. Native Zstandard accepted all 65 Rust encodings. Native libzim read all 4,001 nonredirect items after substituting one Rust-encoded frame in a real archive. A streaming prototype also wrote a single pledged frame above 1 GiB. The published reader can allocate from a claimed output size up to the caller's ceiling and its match-distance validation omits part of the declared history-window policy. An experimental change removes the large eager allocation. The single-frame writer prototype restarts history between jobs and lacks the accepted level range and worker behavior of the current writer. On one real cluster at the default level 19, native took 0.65 s for 208,698 bytes and whole-frame Rust took 1.63 s for 211,251 bytes. Fix and review the decoder policy first. Gate writer adoption separately on single-frame large items, error/flush behavior, level semantics and realistic throughput. [Candidate source](https://docs.rs/crate/zstd-rs/0.1.0/source/)

A second Rust reader, `oxiarc-zstd 0.4.2`, decoded the same 65 frames, matching all 128,005,261 bytes with explicit output limits. It exposes independent output and window bounds and verifies checksums. Its `oxiarc-core` dependency still emitted 35 unique unsafe-code diagnostics in the tested profile, including CRC code. Another option, `ruzstd 0.9.1`, uses unsafe pointer operations in its ring buffer and requires the caller to compare checksums. The no-production-dependency candidate is the shortest path to enforcing an unsafe-free codec graph. [oxiarc-zstd source](https://docs.rs/crate/oxiarc-zstd/0.4.2/source/) · [ruzstd source](https://docs.rs/crate/ruzstd/0.9.1/source/)

**XZ.** The candidate reader decoded nine native configurations covering checksums, multiple blocks and filter chains. Native XZ accepted five Rust encoder presets, and native libzim independently read all 140,297 expected content bytes from a Rust-writer ZIM. The high-level Rust reader verifies block payload checksums and index CRCs, but counts index records without comparing every record's sizes to the blocks it decoded. Footer backward-size validation is also missing. The alternate low-level parser has narrower filter-chain support. Preserve native-format validation as well as dictionary memory, compressed-input, output and block-count limits before switching. A scratch SHA-256 substitution built with unsafe Rust forbidden across the isolated codec graph and passed the same 14 interoperability cases. Its dependency requires additional license provenance and cryptographic review before distribution. [Upstream XZ reader](https://docs.rs/crate/lzma-rust2/0.25.0/source/src/xz/reader.rs)

Native liblzma selection also depends on the build environment. The companion release binary used for these checks contained the bundled `lzma-sys` 5.2.5 fallback, which does not appear in its dynamic-library list. A different build using system pkg-config can link a different liblzma version. Record the selected C source or library version alongside the Rust lockfile for each release until the native decoder is replaced.

**Beyond codecs.** Establish a release profile with the C ABI and legacy mapping disabled. Track the target, host/build and test graphs independently. The original ten Linux configurations included 143 distinct Cargo package IDs and 4,427 Rust files. The Glass engine's baseline release graph had 18 target-role packages with unsafe diagnostics despite forbidding unsafe Rust itself. The revised reader build graph fell from 70 to 37 package/versions, including build-time and proc-macro dependencies. The default writer fell from 75 to 51, and the companion from 117 to 95. Re-audit rayon/crossbeam, parking_lot, LRU/collections, flate2/miniz, rustix, Unicode/ICU4X and crypto for the chosen target. Build/FFI tools, native test oracles and shipped archive parsers have different exposure. A practical release claim should explicitly identify the trusted standard library, OS and audited dependency exceptions. A requirement of zero transitive unsafe Rust needs evidence that each reachable dependency meets it.

## Compatibility, performance and reproduction

* The revised Linux reader, default writer and all-features builds passed **88, 152 and 161** unit/integration tests, plus **6, 7 and 7** doctests respectively. These profiles overlap. Tests included native zim-tools, the external builder and C/C++ smoke programs. Reader-only all-targets compilation, all-features library Clippy and formatting passed.
* All five real ZIMs passed checksum and structural integrity checks. The corpus includes English Climate Change, English Nollywood, both Ray Charles fixtures and Chinese Chemistry. Independent native comparison also covered an aligned Nollywood variant with 4,596 entries. This caught two storage migration pitfalls, a header title pointer legitimately embedded in a cluster and legal trailing padding after a Zstandard frame. Regressions cover both, including guarded reads. The sparse extended-cluster test read beyond 4 GiB under a 128 MiB process address-space limit without populating the decoded cluster cache.
* The companion passed 63 workspace tests including the real fixtures and all 120 ordered search/suggestion reference lists. Six native writer comparisons passed. Across both Xapian 1.4 and 2.0, the baseline and revised tools produced the same results for each CJK query and byte-identical logical snapshots. Existing interoperability differences remain for newer Han characters and, with Xapian 2.0, two fullwidth queries.
* Seven paired warm-file-cache release measurements on three archives found first open plus a single lookup took 10.5–12.7 µs, down from 19.4–35.6 µs. Repeated path lookups took 1.96–2.85 times as long, directory scans 1.51–1.72 times and checksum verification 1.08–1.25 times. A separate four-thread hot-key workload cost 1.09–1.16 µs per lookup versus 0.23–0.30 µs before. Repeated access to one hot key issued zero additional positional reads after warming. Eleven paired Zstd rebuilds per archive yielded byte-identical outputs, with Chemistry 7.6% faster and Nollywood 1.1% slower. These benchmark snapshots preceded the final configurable limits and handle-verification edits. Cold disks, other operating systems, production tail latency and concurrent mixed workloads need separate measurements.

Run the commands below from the MIT checkout. Install the documented liblzma build prerequisites. For the full integration matrix, install the native zim-tools in the location expected by the integration tests, supply the native helper through `XAPIANBUILDER`, stage the CI checksum-verified ZIMs in `zim-cache/` and set `ZIMRU_REQUIRE_FIXTURES=1`. This branch tracks the reviewed Cargo.lock for reproducible dependency selection. Test results, exact dependency graphs, codec experiments and per-sample timings are in the accompanying evidence archive.

```sh
cargo build --locked --all-features
cargo test --locked --all-features
cargo test --locked --no-default-features
cargo test --locked
cargo check --locked --no-default-features --all-targets
cargo clippy --locked --all-features --lib -- -D warnings
cargo fmt --all -- --check
```

The highest-value remaining change is a bounded Rust decoder for each format. Accept it only when it validates native format invariants, agrees on representative archives, preserves legitimate padded and large files, and meets an explicit memory policy at the archive and concurrent-request levels. Writer atomic publication and bounded HTML ingestion can proceed in parallel.
