# Adversarial and performance review of the positioned reader

18 November 2026. The starting point was the privately published MIT archive reader `96447ac` and GPL search companion `99a2e48`. The performance comparison also includes the earlier mmap reader `061afbc` and companion `2162bfa`. The revised archive code measured in this report is `6acf7fd`. The paired GPL tool uses that reader and moves its original file handle into the Glass range reader. Both projects retain their own source histories and licenses.

## Findings and fixes

| Impact | What the review found | Outcome |
|---|---|---|
| High · silent export data loss | Two distinct entries could normalize to the same output name. An ordinary entry could also occupy the exporter's exception or diagnostic path. An atomic rename could then replace the other entry and the export could report success. | The exporter plans destinations before creating or modifying the output, including redirect names, exception routing, internal temporary names and the diagnostic log. Ambiguous plans return an error. Ordinary file/directory prefix conflicts still use the existing exception convention. On a real Climate Change export, native libzim agreed on all 3,985 article payloads and 16,566 immediate symlink targets, including 131 relocated outputs. [Planner](../src/bin/zimdump.rs) · [Tests](../tests/dump_integrity_regressions.rs) |
| High · resource use on concurrent reads | Concurrent misses on one compressed cluster could trigger one allocation and decode per request. The resident cache budget took effect after that work. | Cached reads now share one in-flight result per cluster ID. Other IDs can proceed independently. Failures can be retried and an evicted result remains valid for the readers that requested it. Twelve simultaneous readers received the same shared cluster in regression testing. Explicit uncached reads and different clusters still need aggregate admission in memory-constrained deployments. [Archive](../src/archive.rs) |
| High for interoperability · valid compressed data rejected | The exact-slice decoder used the first Zstandard frame's pledged size as the destination size for the whole input. The XZ archive reader continued past the verified stream footer into alignment padding. | Both APIs now respect the distinction between exact input and an estimated on-disk cluster interval. Complete frame sequences and padded physical regions were tested with native tools. The XZ reader retains its native checksum/index verification, decoder-memory limit and decoded-output limit. Ten native-compatible archive variants plus three alignment/original comparisons passed full walks. [Codecs and regression tests](../src/cluster.rs) |
| Medium · false empty or incomplete iteration | A metadata or I/O error in title, namespace or prefix initialization could appear to the caller as a successful empty result. Metadata errors from positioned slices also reported a slice-relative offset. | Result-returning iterators now yield the initialization error once, then terminate. Exact-size iterators account for the error item, and error positions are archive-relative. Directory parsing validates declared trailing parameter bytes. Binary-search probes handle the short layout of retired linktarget/deleted records. Materializing one returns an explicit unsupported-format error because it has no item location. [Directory parser](../src/dirent.rs) · [Iterator tests](../tests/positioned_archive.rs) |
| Medium · writer retry and failure | Failure to open an output could discard the selected main page. Failure after buffered data had begun draining or after an asynchronous write could leave a partially built creator that callers could continue using. | A failed open preserves buffered entries and the main page. Irrecoverable writer failures terminate the build and later fallible writes/finalization return an error. Short chunk sequences remain correctable. Native libzim verified the main page, article and metadata after an ordinary retry. Native XZ and libzim also verified all ten writer presets and 40 item payloads. [Writer and tests](../src/writer.rs) |
| Medium · optional C API and file handles | The C writer accepted a zero-length chunk with no active item. Several header comments overstated allocation and memory guarantees. The GPL CLI allocated a third file descriptor for the same open archive. | Empty chunks now use the same state validation as nonempty chunks. Corrected the C contract and ran C/C++ smoke tests. The search CLI uses two handles with the same file identity. [C header](../include/zimru.h) |
| Performance · hot metadata contention | Even a cached page hit acquired an LRU lock and updated a shared reference count. Four workers contending on the same key incurred a large CPU cost. The warmed test produced no additional positioned reads for those lookups. | Half of the 1 MiB page-content budget holds immutable lookup pages accessible without a lock or reference-count update. Collisions use the rotating half. Path scans can read already pinned pages and leave empty fixed slots available for later point lookups. [Storage implementation](../src/archive/storage.rs) |

## Performance on the final implementation

Seven counterbalanced rounds covered 30 archive/workload pairs on three revisions, giving **630 observations**. The ratios below are final median elapsed time divided by the corresponding reference median, with the range taken across the comparable archives. A ratio below one means the final build took less time. [Raw samples](review-data/archive-benchmark.csv)

| Workload | Final ÷ original mmap | Final ÷ published positioned reader |
|---|---:|---:|
| Open plus one exact lookup | 0.55–0.68× | 0.80–0.87× |
| Serial, repeated key | 1.37–1.42× | 0.59–0.66× |
| Serial, varied keys | 1.47–3.11× | 0.65–0.97× |
| Four workers, repeated key | 1.05–1.26× | 0.25–0.28× |
| Four workers, varied keys | 1.41–3.39× | 0.40–0.78× |
| Serial directory scan | 1.31–2.03× | 1.09–1.19× |
| Four-worker directory scan | 1.78–2.93× | 0.88–1.28× |
| Archive checksum | 1.12–1.25× | 0.99–1.07× |
| Decode every blob | 0.87–1.04× | 0.95–1.02× |
| Zstd level-3 recreate, one worker | 0.95–0.99× | 0.98–1.05× |
| Zstd level-3 recreate, four workers | 0.94–1.06× | 1.00–1.06× |

The four-worker repeated-key test on Climate, Chemistry and Nollywood took **0.43, 0.46 and 0.30 µs per lookup**. On Climate, serial varied lookups still took 2.20 µs and the full serial directory scan took 4.98 ms. The revised directory scan trades some traversal speed for better subsequent random lookup behavior. All 84 timed archive rebuilds matched the corresponding reference bytes. The rebuild benchmark disabled external index creation.

The sample unit for parallel lookup is aggregate elapsed time divided by total completed lookups. It describes throughput under four workers, not individual request latency. Timings use release builds and warmed filesystem data on shared x86-64 Linux. The three real archives contain roughly 4,600 to 20,600 directory entries. We alternated execution order, checked returned entry IDs or aggregate content against the other builds, and verified each recreated archive's SHA-256 and internal checksum. Climate's complete cluster scan is excluded from the original/revised cluster comparison because the original reader rejects a valid cluster in that archive. Cold storage, multi-GiB production directories, macOS, Windows and long-running service tail latency were outside these measurements.

### Why path scans have separate cache admission

An intermediate implementation let a full directory scan permanently populate the 128 fixed slots. On Climate, a subsequent series of 4,096 valid keys drawn from the upper three quarters of the directory caused **1.077 additional positioned reads per lookup**, up from **0.193** on the published LRU. Making path scans skip fixed-slot admission restored **0.193**. The corresponding upper-half workload returned from **0.874 to 0.247**. We also tested 32 and 64 fixed pages. Both smaller allocations reduced the penalty for some input orders and gave up benefits on other shared lookups. The retained implementation addresses the observed cause of the post-scan slowdown. A different point-lookup history can still influence which pages are pinned. [Cache stress measurements](review-data/cache-admission.csv)

### Search and index creation

The corrected release CLI returned identical complete JSON across all **120 libzim reference queries** on Climate and Nollywood. In 31 paired runs on each of eight search and suggestion workloads (248 pairs), the final executable's median was **1.16–2.38 ms** including process startup. Median peak RSS fell by **84–752 KiB** in all eight. Broad Climate search was 1.602 ms versus 1.489 ms originally. Its median of paired percentage differences was +2.1% (descriptive 95% bootstrap interval +0.1% to +10.2%). The other seven timing intervals included zero. These measurements describe short CLI invocations with warmed files. [Timing and RSS by workload](review-data/search-benchmark.json)

The index-builder code was identical in the reviewed and revised branches. On a 50,000-document corpus, nine paired title and nine paired full-text runs of the original and published releases showed equal median peak RSS for each mode. Their timing intervals were wide. All four resulting Glass databases passed native `xapian-check`, and the title/full-text logical snapshots matched by mode.

## Remaining priorities

1. **Native compressed-input parsers remain the largest memory-safety boundary.** The archive reader invokes native liblzma and Zstandard. The Rust XZ encoder has transitive unsafe Rust. Selecting native libraries at build time, verifying linkage per release and reviewing the pure-Rust decoder candidates remain independent work. [Codec and dependency inventory](memory-safety-review.md)
2. **Archive limits bound individual operations.** Multiple distinct cluster decodes, outstanding blobs, and a transient decoded-buffer copy can exceed a cluster or cache limit in aggregate. The C open API exposes default archive limits only. A C metadata-cache miss also holds the handle's cache lock across retrieval. The CLI writer's full HTML reads, optional gzip inflation, input batches, codec scratch space and worker threads require separate limits.
3. **File publication has explicit assumptions.** The writer can truncate the destination before successful completion. Extraction preflight compares exact component spelling and assumes exclusive control of the output tree. Case- or Unicode-equivalent names on other filesystems can still alias. A later I/O error can leave earlier files in place. A redirect chain involving a target relocated only at runtime due to pre-existing filesystem contents can still reference the original path. The reader assumes a stable source inode for coherent cached data.
4. **Compatibility and speed depend on the workload.** Foreign callers must honor pointer lifetimes and synchronization. Retired directory markers cannot be materialized as archive items. Native CJK differences for newer Han characters remain. A monotonic file traversal pays different costs from a hot shared lookup. Elevated peak RSS or slower query tails on much larger archives require measurement with representative deployments.

## Verification

The final Linux reader-only, default writer and all-features profiles passed **98, 165 and 174** tests respectively, plus **6, 7 and 7** doctests. The profiles overlap. The three CI archive checksums were verified and native zim-tools and the reference builder were available during these runs. Formatting, reader-only all-targets compilation, all-features library Clippy and the C/C++ smoke suites passed. The companion workspace passed 63 tests with both real fixtures. Native English index-writer comparisons also passed across six language/mode combinations.

A repeat of the Xapian 1.4 CJK test passed the ordinary Chinese, Japanese and Korean corpora (63/63 queries). Six of twelve newer-Han queries and both newer-Han index snapshots still differed between the native and Rust implementations. The earlier comparison with Xapian 2.0 also found two fullwidth-query differences. The 2.0 comparison was not repeated for this review.
